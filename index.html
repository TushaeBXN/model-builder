The problem

Most vision AI projects fail before a model is ever trained — because the spec was wrong.

Wrong label definitions. Wrong edge cases. Wrong architecture for the latency requirement. Wrong output format for the downstream system. model/builder fixes that — before any training begins.

  • ×Label definitions too vague to annotate consistently
  • ×Edge cases identified after labeling thousands of frames
  • ×Architecture chosen before understanding latency requirements
  • ×Binary output when downstream needs graded severity
  • ×No adversarial review until the model is already in production

Features

Built around what actually matters

⚔️
Adversarial Mode

Toggle it on and every spec Claude generates is immediately followed by a critique — Claude playing the role of a skeptical senior ML engineer trying to find the gaps.


Not generic advice. Pointed critique grounded in what you actually described. Specific failure modes. Missing edge cases. Annotation ambiguities. Deployment risks. Most spec tools tell you what to build. This one also tells you why it might fail.

Adversarial Review

1. "Flooded" vs "wet road" boundary is undefined — annotators will diverge on 2–4 cm water depth. This alone kills recall consistency.

2. Rain-at-night combines two failure modes simultaneously. Your spec addresses them separately; the model will see them together.

3. No mention of camera angle variance. A feed 8 meters high reads flooding differently than one at 3 meters. Both exist in a city deployment.

📎
Grounded to Your Footage

Drop a real frame from your camera feed. Claude analyzes the specific scene — lighting conditions, camera angle, what a false positive would literally look like in this footage. The spec it generates references what it actually sees, not a generic description of your use case.

Output

Five sections — each a working artifact

Not summaries. Not suggestions. The actual spec content your team can execute against.

01 · PROBLEM
Problem Specification
  • Exact positive/negative case definitions
  • Annotation ambiguities to resolve first
  • Output format with label names
  • Top false-positive risks
02 · DATA
Data Strategy
  • Minimum labeled data + reasoning
  • Full annotation schema
  • Class balancing approach
  • Train / val / test split
03 · ARCH
Model Architecture
  • Specific model names, not categories
  • Two-stage screening decision
  • VLM prompt engineering strategy
  • Inference cost per image
04 · TRAIN
Training Plan
  • Fine-tuning method (SFT / LoRA)
  • Cross-check rephrasing technique
  • Eval benchmark with rejection cases
  • Target accuracy range
05 · DEPLOY
Deployment Plan
  • Inference pipeline architecture
  • Production monitoring metrics
  • Drift detection + retraining triggers
  • Alert and escalation logic
Getting started

No install. No build step.

A single HTML file. Open it in a browser and you're running — inside claude.ai or with your own API key.

# Clone and open — that's it git clone https://github.com/TushaeBXN/model-builder cd model-builder open model_builder_v2.html
# Or serve locally python3 -m http.server 8080 # → http://localhost:8080/model_builder_v2.html
⚠ Running outside claude.ai? Add "x-api-key" and "anthropic-version" to the fetch headers. Never commit API keys — for anything beyond local use, put a lightweight proxy in front.

The stack is intentionally minimal. No npm, no build pipeline, no server dependency.
